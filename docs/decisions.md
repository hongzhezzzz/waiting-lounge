# Decisions log

Non-obvious choices we've made, one or two lines each. Append-only — if a decision is later reversed, add a new dated entry rather than editing the old one. That way you can see the history.

Format: `YYYY-MM-DD: <decision> — <one-line reason>`

---

- 2026-05-06: Use git locally with no GitHub remote yet — version control gives us rollback without needing an online account. We can add GitHub later if/when we need backup, sharing, or auto-deploy.
- 2026-05-06: Repo lives inside the user's Dropbox folder — convenient because it's already synced across the user's devices. Small risk: Dropbox can occasionally sync the `.git/` directory mid-write and corrupt history. If we ever see "fatal: bad object" or similar, that's the cause and we move the repo out of Dropbox.
- 2026-05-06: Default git branch is `main` — modern default, no other reason.
- 2026-05-06: Phase 1 hook writes to `~/.waiting-lounge.log` (the user's home folder), not into the repo — keeps event logs out of git history and out of Dropbox sync.
- 2026-05-06: Phase 2 frontend uses Next.js 14 App Router + Tailwind, scaffolded by `create-next-app` with TypeScript, ESLint, `src/` directory, `@/*` import alias — matches roadmap §5 and gives clean route folders for the screens listed in spec §7.
- 2026-05-06: Visual default is warm off-white (#FAF7F2) background, sage accent (#7FA98A), amber alert tone, generous whitespace, rounded-2xl cards, Geist Sans + small mono touches — aims at spec §14 "lightweight, friendly, slightly playful, low-pressure." Easy to swap once the user reacts.
- 2026-05-06: Demo Claude-needs-you alert wired as a small floating "▶ demo alert" button on `/chat` and `/board` — lets the user feel the alert without a backend. Removed/relabelled when Phase 5 wires it to real events.
- 2026-05-06: Mock chat replies happen in-component with a fake 1.2s peer reply — kept obvious as a demo (peer always says "(demo) — …") so spec §7 rule about "no fake data masquerading as real" stays honored.
- 2026-05-06: Phase 3 backend is TypeScript run via `tsx watch` rather than ts-node-dev — `tsx` is the simpler, well-maintained option in 2026 and needs no extra config. Same dev ergonomics (auto-restart on save).
- 2026-05-06: Backend port is 4000, frontend stays on 3000 — keeps the two dev servers separable and matches the placeholder `NEXT_PUBLIC_SOCKET_URL` default.
- 2026-05-06: Server **never logs message bodies** — only metadata (room id, sender handle, length). Spec §11 mandates "temporary message storage"; even though MVP storage is just in-memory, we set the precedent now so the production migration in Phase 6 doesn't accidentally start persisting bodies.
- 2026-05-06: `/chat` defaults to live (real socket); `?demo=1` keeps the fake-data path so the user can compare or show the app off without a backend.
- 2026-05-06: Anonymous handle generated server-side per connection (e.g. `gentle-diff-232`) — pulls from short colour/adjective + noun + 3-digit lists in `backend/src/lib/identity.ts`. No persistent identity in MVP.
- 2026-05-06: Block list is in-memory and per-socket — when a user blocks a handle, that handle is excluded from future matches *for the blocker only* during their current session. Persistent blocking lands in Phase 6 with the database.
- 2026-05-06: Known quirk on this machine — Next.js dev (HMR + file watcher) sometimes misses changes to files on `/mnt/c/...` (Windows filesystem under WSL2 + Dropbox sync), leaving the **server-side bundle stale** while the URL still returns 200. Symptom: page renders the previous version's content even after edits. Fix: stop the dev server, `rm -rf web/.next`, restart `npm run dev`. Hit this once during Phase 3 testing — the user saw fake chat data on `/chat?tag=...` because the SSR bundle for the chat route was cached from before the live-mode rewrite.
- 2026-05-06: "Find a new match" after peer-left was a `<Link>` to the same URL, which Next.js treats as a no-op. Replaced with a `searchNonce` state in `LiveChatWindow` — incrementing it forces the join effect to re-run and emit a fresh `join_queue`. Same trick is wired into the in-chat header "New match" link via an optional `onNewMatch` callback on `ReportBlockControls`.
- 2026-05-06: Phase 4 board lives at `/api/board` on the same Express server as the socket — one process to run, one CORS config. Endpoints: `GET /api/board?tag=`, `POST /api/board`, `POST /api/board/report`. In-memory `Map<id, BoardPost>`. 24-hour TTL, swept every 5 minutes. 10-second per-IP post cooldown (basic rate limit). Hide threshold: 3 reports auto-hide a post.
- 2026-05-06: Board posts get a freshly generated handle on every POST (no carryover from any chat handle) — there is no continuity of identity between a person's chat handle and their board posts. This is intentional for now: posting feels disposable, and we don't accidentally tie chat history to board history. Persistent identity is a Phase 6+ decision tied to durable storage.
- 2026-05-06: Frontend `MessageBoard` polls the API every 8 seconds — quick enough that posts from another window appear within seconds, slow enough that idle traffic is small. Replaced with a websocket push if board chat ever feels laggy.
- 2026-05-06: Board seeded with two welcome posts at backend startup so a fresh user doesn't land on an empty board (spec §9.2: "Do not leave the user on an empty spinner"). Seed posts are clearly meta ("Welcome. Posts vanish in 24h…") so they don't masquerade as real activity.
- 2026-05-06: **Phase 5 privacy paragraph** (per ground rule #6). The Claude Code hook payload path is now: Claude → `local-hook/hook.js` → POST `http://localhost:4000/api/agent-event`. Sanitization is double-enforced: (a) the hook script discards stdin entirely — never parses, never inspects, never logs the raw payload — and only sends a four-field object `{anonymousDeviceId, status, client, timestamp}`; (b) the backend route rejects any payload containing keys other than those four, so even if a future hook bug leaked something into the body, the server refuses it with `400 Unexpected field`. The hook swallows all errors (timeouts, connection failures, malformed responses) so it can never block or surface anything to Claude Code. Verified end-to-end: piping `{"prompt":"DO_NOT_LEAK","cwd":"/tmp/secret"}` to the hook produced only `agent_event {deviceIdShort, status, delivered}` in the backend log — zero leakage.
- 2026-05-06: Pairing model is **option C from roadmap §8.3** — `node local-hook/hook.js pair` prints a one-time URL to stdout. The user opens it once; the browser stores the deviceId in localStorage. Deliberately rejected option A (deviceId always in URL — easy to leak via referrer/screenshot) and option B (manual pairing code — extra step the user has to type). The pair subcommand also creates the `~/.waiting-lounge/device_id` file with mode 0600 if it doesn't exist.
- 2026-05-06: One global `ClaudeNeedsYouOverlay` mounted at the layout level (driven by the `AgentStatusProvider` context) — replaces the per-page overlays from Phase 2/3/4. Per-page "▶ demo Claude-needs-you alert" buttons now call `simulate("needs_attention")` on the provider instead of opening their own overlay, so the demo path and real path go through the exact same code.
- 2026-05-06: Header gets a `<LiveAgentStatusBadge />` that reads from the provider — shows "Not paired" until the user pairs the browser, then shows live status. Per-page badges (which were redundant after the global one) were removed from /chat, /board, /join.
- 2026-05-07: **Phase 8 deploy.** Frontend on Vercel (`https://waiting-lounge.vercel.app`, auto-deploys from `main`), backend on Render (`https://waiting-lounge.onrender.com`, free tier, auto-deploys from `main`), Postgres on Supabase. CORS (`ALLOWED_ORIGINS` env on Render) covers both `localhost:3000` and the Vercel URL. Local hook reads its backend URL from `~/.waiting-lounge/backend_url`.
- 2026-05-07: Frontend picks the backend URL at **runtime** based on `window.location.hostname` (localhost → `localhost:4000`, anything else → the Render URL) when no `NEXT_PUBLIC_BACKEND_URL` env var is set. Avoids needing a Vercel build-time env var for the friend pilot. If we later move the backend off Render, set the env var on Vercel instead of editing this fallback.
- 2026-05-07: Backend keeps a **last-known status per device** in memory and replays it to a browser as soon as it `register_device`s. Without this the badge stayed "Not connected" until the next hook event, defeating the intended UX (Claude starts → user opens lounge → badge already shows "working"). Stored in-memory only — when Render free-tier sleeps the backend (~15min idle) the map is wiped; the badge will show "Not connected" until the next hook event arrives. Promoting this to Postgres is a candidate fix if friends complain.
- 2026-05-07: **`PostToolUse` hook → `waiting`** wired up so the badge flips back to "Claude is working" after the user approves a permission and the tool actually runs. Without it, the badge stayed amber for the rest of the assistant turn after approval. Implemented as a new `resume` subcommand in `local-hook/hook.js` plus a `PostToolUse` entry in `.claude/settings.json`.
- 2026-05-07: **Known badge edge cases left unfixed** (deferred — none are blocking the friend pilot):
  1. *Interrupt/deny via the interrupt button leaves badge stuck at "Claude needs your attention".* When the user hits the interrupt button while a permission dialog is up, neither `Stop` nor `PostToolUse` fires, so nothing clears the amber state until the next `UserPromptSubmit`. Fix candidate: a frontend TTL (after ~90s, treat `needs_attention` as `done`).
  2. *Closed Claude Code freezes the badge at last status forever.* No `SessionEnd` → `done` mapping today. Same TTL as #1 would cover it.
  3. *`Notification` fires for non-permission idle nudges too.* Those repaint the badge amber even when Claude isn't actually waiting on the user. Lives with #1 — TTL plus, eventually, distinguishing notification subtypes if Claude Code's hook payload exposes them.
  4. *Render free-tier sleep wipes the in-memory last-status map.* Long idles → "Not connected" until next hook event. Fix: persist last-status to Postgres.
  5. *Multi-folder collision.* Two Claude Code sessions on the same machine share one device id; their events interleave on the same badge (newest wins). Fine for now since identity is per-machine, not per-folder; revisit if friends actually run two concurrent agents.
- 2026-05-07: **Phase 11 — accounts and points.** First time the lounge has any persistent identity. Sign-in is **6-digit OTP email via Supabase Auth** (chosen over magic-link to avoid the orphaned-tab UX trap, and over GitHub-only so non-GitHub friends can sign in). Anonymous handles still appear in-game — auth is for *persistence of points*, not de-anonymizing. The local hook is **untouched** and still only sends the 4-field sanitized payload.
- 2026-05-07: **Phase 11 game design — Spot the Bug.** Two players see the same 8-line buggy snippet; first to click the offending line wins the round. Picked over Type Race (swap recommended by Plan agent — keyboard speed is a worse fit for a dev audience than real bug-finding skill, same backend cost). Bank starts at ~30 hand-curated snippets across JavaScript / Python / SQL covering off-by-one, async ordering, JS coercion, mutation-during-iteration, and other classic gotchas (`backend/src/games/spotTheBug/snippets.json`). Round count is 3/6/10 for 1/5/10-min games; round timeout 45 s; post-round pause 2.5 s.
- 2026-05-07: **Phase 11 staking model.** Fixed 100-point ante v1, both players ante at game start, winner takes 200, tie returns stakes. Starting balance 1000 pts on first sign-in. Picked fixed ante over a chooser to keep the friend-pilot UX trivial; player-chosen ante can be added in Phase 13+.
- 2026-05-07: **Phase 11 atomic points.** All point mutations go through `backend/src/games/transferPoints.ts` inside a single Postgres transaction with `SELECT … FOR UPDATE` ordered by user id (prevents deadlock between concurrent games). At ante time we also write a `pending_refunds` row per player; settle marks them `processed_at = now()`. If the backend dies mid-game, on next startup `processStalePendingRefunds()` credits the antes back and marks the `game_rounds` row `outcome = 'aborted'`. Smoke-tested both happy-path settle and cold-start refund against the live Supabase DB; results: ante 100 → balance 900, win → 1100, tie → 1000, abort → 1000.
- 2026-05-07: **Phase 11 socket auth is optional, not required.** The middleware verifies a Supabase JWT if present; if absent or invalid the connection is anonymous (still works for chat/board/lounge). Game events (`queue_for_game`, `game_action`) check `socket.data.userId` and reject if missing. Keeps the existing flows working for users who haven't signed up yet.
- 2026-05-07: **Phase 11 cross-machine room reuse.** Game peers join the same Socket.IO `roomId` model that chat already uses (instead of building a parallel "game room" concept). Means chat-while-gaming is essentially free in Phase 14. Game framework is registry-driven (`backend/src/games/index.ts` registers each game type's runner constructor) so Phase 12's Brain Bet only needs a new resolver class.
- 2026-05-07: **Phase 11 Node 18 polyfill.** `jose` v6 went webapi-only and expects `globalThis.crypto`, which Node 18 doesn't expose. Polyfilled at the top of `backend/src/server.ts` from `node:crypto.webcrypto`. Harmless on Node 20+ where `globalThis.crypto` is already set; can be removed once the user's local env is on 20.
- 2026-05-07: **Phase 11 anti-abuse coverage.** Self-match (same user_id on both sides of `queue_for_game`) is rejected by the queue's eligibility filter. Device-account binding is keyed on `device_id` and 409s on a second account trying to claim the same device. Disconnect-during-game gives a 10 s grace timer before forfeit (handled by the resolver — same-user reconnect cancels the timer). Cold-start refund covers any game that died before settle. Skipped for v1: per-IP socket-level rate limit on game starts (5 friends, low blast radius).
